# Harness 结构设计

仅当任务已分类为 Loop、Workflow 或 Graph Engineering，或需要评估工作区整体结构时读取本文。

## Harness、Loop 和 Graph

Harness 是 Agent 的整体工作环境：

| 层 | 解决的问题 | 常见入口 |
| --- | --- | --- |
| 入口与约束 | 什么请求必须触发什么规则 | `AGENTS.md`、README、skill description |
| 上下文与知识 | Agent 需要什么证据和说明 | `docs/`、源码、配置、权威文档 |
| 执行能力 | 怎样完成动作 | skills、CLI、平台工具、scripts |
| 观察与验证 | 怎样确认真实结果 | tests、E2E、diff、日志、运行结果 |
| 失败处理与保存 | 失败后返回哪里，长期内容写哪里 | Loop、Workflow、既有事实源 |

Loop 描述一个目标如何重复执行并停止。Workflow 描述多个步骤、角色或 Loop 如何连接。Graph Engineering 只在多个 Loop 必须监督彼此的目标、方法、指标或结果时才需要；有流程图、并行或条件分支并不等于 Graph Engineering。

## 设计 Loop

只有目标需要重复执行时才使用 Loop，并明确：

1. 初始状态和每轮输入。
2. 动作及允许修改的范围。
3. 独立检查器和可验证的通过条件。
4. 失败后回到哪个动作，哪些证据必须重建。
5. 最大总尝试次数、间隔、时间或成本上限。
6. 无法继续时停止还是交给用户。

每次修复后重新验证受影响的后续步骤。旧截图、旧构建、旧 Review 和已过期结果不能代表最终状态。

## 设计 Workflow

存在稳定分支、并行、汇合或角色交接时，先设计 Workflow。每个节点至少写清：

| 项目 | 要回答的问题 |
| --- | --- |
| 触发与输入 | 什么状态进入，读取哪些真实对象 |
| 负责人 | 主 Agent、subagent、脚本、平台还是用户 |
| 动作范围 | 能读什么、能改什么、禁止什么 |
| 输出 | 产生什么结构化结果或真实状态 |
| 完成条件 | 用什么命令、证据或平台状态判断 |
| 失败去向 | 返回哪个节点、停止还是交给用户 |

Workflow 还必须满足：

- 只保留一个共享状态源。
- 并行节点不写同一工作区；代码改动使用隔离 worktree。
- 汇合节点等待所有必需输入。
- 不可逆动作由明确的人工确认节点授权。
- 每条回边都有停止条件和重试上限。

## 判断是否需要 Graph Engineering

只有单个 Loop 或普通 Workflow 出现以下问题时才增加监督 Loop：

- 单一指标变好，但真实结果变差。
- 执行 Loop 无法质疑目标或验证方法。
- 多个 Loop 的速度、质量、成本或风险目标互相冲突。
- Agent 能通过修改 Case、降低阈值或改变测量方式让自己“通过”。

至少补齐：

1. 执行 Loop：完成具体目标并做快速检查。
2. 结果监督 Loop：用另一组真实结果检查是否只优化了单一指标。
3. 方法审查 Loop：低频检查策略、Case 和指标是否仍有效。
4. 外部判断：价值取舍、不可逆动作和目标变化由用户或明确负责人决定。

保护真实锚点、核心检查和独立判断。不要仅因术语流行就增加通用编排框架；先用既有状态源、skills、原子 CLI 和 tests 表达，只有它们无法满足状态恢复、并发调度或跨进程执行时再评估专用运行时。
